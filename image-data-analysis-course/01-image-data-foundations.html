Understanding Images as Data

Before you can analyze an image dataset, you need to stop seeing images as "pictures" and start seeing them as grids of numbers. This file rebuilds that intuition from zero — no computer vision background assumed.

01 What exactly is an image?

To a person, a photo is a scene. To a computer, it is a table of numbers with no idea what a "cat" or a "sky" is. Everything you'll do in this course sits on top of that one fact.

pixel
simple explanation

A pixel is one tiny colored square. Zoom into any digital photo far enough and it dissolves into a grid of these squares.

technical definition

A pixel ("picture element") is the smallest addressable unit of a digital image — a single value (grayscale) or set of values (color) that the image array stores at one grid position.

analogy

Think of a stadium mosaic display: thousands of individually-colored panels that only form a picture when you step back. Each panel is one pixel.

when it's useful

Every single image operation — brightness, blur, resizing, feature extraction — is really just math applied to pixel values.

when it's not the right lens

Thinking "pixel by pixel" doesn't help when you want to reason about shapes, objects, or textures — for that you need groups of pixels, which is where later sections (gradients, HOG, convolution) come in.

So an image is fundamentally: Image → Pixels → Numbers. A photograph is a big grid; each grid cell holds one or more numbers; and those numbers are all a computer ever sees.

The vocabulary you need before going further

channel
simple explanation

A channel is one "layer" of color information stacked behind each pixel. A grayscale image has 1 channel (just brightness). A color image usually has 3 (red, green, blue).

technical definition

A channel is a 2D slice of an image array holding one component of the pixel's color model, stacked along a third array axis.

analogy

Like three transparent colored sheets (red, green, blue) laid on top of each other — stack them and you get full color; look at one alone and you get a grayscale-like intensity map of just that color.

when it's useful

Whenever you need to know why a color image's shape ends in 3, or why some operations (grayscale conversion, HSV analysis) explicitly reduce or reorganize channels.

when it's not useful

For genuinely grayscale sensors (X-ray, thermal, some microscopy) there's often only one meaningful channel — forcing 3 channels on that data adds nothing.

RGB

Red, Green, Blue — the order most tools (Matplotlib, Pillow, scikit-image) expect. Each channel typically ranges 0–255 for 8-bit images.

BGR

Blue, Green, Red — the same three numbers, reversed order. This is OpenCV's default when it loads an image, purely for historical reasons.

⚠ common mistake

Loading an image with cv2.imread() (which returns BGR) and then displaying it with plt.imshow() (which assumes RGB) without converting first. The colors come out looking wrong — blues and reds swapped — not because the data is corrupted, but because the two libraries disagree on channel order.

A few more terms you'll see constantly, defined briefly here and used precisely for the rest of the course:

termmeaning
resolutionThe image's width × height in pixels — e.g. 512×512. Higher resolution means more detail, but also more data to process.
grayscaleAn image with a single intensity channel per pixel — no color, only "how bright."
alpha channelAn optional 4th channel storing per-pixel transparency (common in PNGs). Rarely relevant for standard photo analysis unless you specifically need transparency.
bit depthHow many bits are used per channel value. 8-bit → values 0–255. 16-bit → values 0–65,535 (common in medical/scientific imaging).
image dtypeThe NumPy data type storing those values — uint8, float32, etc. Covered fully in Section 4.

02 2D vs 3D image arrays

Once you accept that an image is a NumPy array, the very first thing worth checking about any image is its .shape — because that one line tells you whether you're looking at grayscale or color data, and how big it is.

what it does

Reads the array's dimensions directly from its metadata — no need to load the whole image again.

why we need it

Shape mismatches are the single most common source of crashes in image pipelines (e.g. feeding a grayscale image where a model expects 3 channels).

import numpy as np
from skimage import data, color

gray = data.camera()                 # a built-in grayscale sample
rgb  = data.astronaut()              # a built-in color sample

print(gray.shape)
print(rgb.shape)
expected output
(512, 512)
(512, 512, 3)
interpretation

(512, 512) means height=512, width=512, and — because there's no third number — a single implicit channel: grayscale. (512, 512, 3) means the same spatial size, but now with 3 stacked channels (R, G, B) per pixel.

common mistake

Reading the shape as (width, height) — it's actually (height, width, channels) in NumPy/OpenCV/scikit-image convention, the opposite order from how Pillow reports .size.

important

"2D array" and "grayscale image" are the same thing here. "3D array" doesn't mean a hologram — the third dimension is channels, not depth. A single color photo is a 3D array; a whole folder of color photos loaded into one array would be 4D: (num_images, height, width, channels).

03 Pixel values

Knowing the shape tells you the grid size. Knowing the values tells you what's actually drawn on that grid.

For the common case of an 8-bit grayscale image:

grayscale intensity scale
0 = black → 255 = white

Everything in between is a shade of gray. A value of 128 is roughly middle gray.

Color images extend this idea per channel — a pixel of (255, 0, 0) in RGB is pure red, (0,0,0) is black, (255,255,255) is white.

You almost never eyeball a 512×512 grid of numbers directly. Instead, you summarize it with a handful of NumPy calls:

what it does

Computes five quick summary statistics for an entire image array in one pass each.

why we need it

These five numbers are the fastest possible health-check for any image — before you even look at it, you already know its size, its numeric type, and its rough brightness range.

import numpy as np
from skimage import data

image = data.camera()

print(image.shape)
print(image.dtype)
print(image.min())
print(image.max())
print(image.mean())
expected output
(512, 512)
uint8
0
255
129.06
interpretation

Line by line: a 512×512 grayscale image, stored as unsigned 8-bit integers, using the full possible range (0 to 255) with an average brightness of about 129 — a fairly mid-toned image overall.

when this is useful

Run this on every image (or a sample) when you first receive a dataset — it instantly flags images that are pure black, pure white, or oddly narrow-range.

04 Image data types

The same pixel value can be stored in different numeric formats, and mixing them by accident is one of the most common (and confusing) bugs in image work.

dtypetypical rangewhere you'll see it
uint80 – 255 (integers)How images are loaded from disk by default (JPEG, PNG, etc.)
float32commonly 0.0 – 1.0What neural networks expect as input
float64commonly 0.0 – 1.0What many scikit-image functions return internally
important — two different operations, often confused

Changing dtype (the container) and changing value range (the contents) are not the same thing, and doing one without the other silently breaks images.

what it does

Two different transformations that both "look like normalization" but behave very differently.

image = data.camera()               # uint8, values 0-255

# (A) changes the CONTAINER only — values are still 0-255
as_float = image.astype(np.float32)

# (B) changes the VALUE RANGE — now scaled to 0.0-1.0
normalized = image / 255.0
expected output
as_float.dtype   -> float32   as_float.max()   -> 255.0
normalized.dtype -> float64   normalized.max() -> 1.0
interpretation

.astype() alone just relabels the numbers as floats — 255 stays 255.0, still "bright white" on a 0-255 scale. Dividing by 255 actually rescales every value into the 0–1 range that most ML models expect.

common mistake

Calling .astype(np.float32) and assuming the image is now "normalized" for a neural network. It isn't — the values are still 0–255, just in a different container. This one mix-up quietly wrecks model training more often than almost any other preprocessing bug.

05 How Python sees an image

Every library you'll touch in this course ultimately hands you back the same thing: a NumPy array. The differences are in convenience functions, default channel order, and what kind of operations each one specializes in.

the pipeline underneath everything
Image → NumPy array → numbers → features

Whichever library loads the image, this is where it always ends up. Feature extraction (File 4) is just further math on these same numbers.

libraryreach for it when…
OpenCV (cv2)You need speed, video, real-time processing, or classical CV operations (thresholding, morphology, contours). Loads as BGR.
scikit-imageYou want scientific-Python-friendly functions with sensible defaults (RGB order, float outputs), built-in sample datasets, and access to feature extractors like HOG and LBP used in File 4.
PIL / PillowYou need simple loading, saving, format conversion, resizing, or basic annotation without a heavier CV toolkit.

In practice, real projects mix all three: Pillow to load a weird file format, OpenCV for fast preprocessing, scikit-image for feature extraction and metrics — converting between them is just NumPy array conversions.

06 First image inspection

Five OpenCV functions cover the vast majority of "just let me look at this image" needs.

what it does

Loads a file from disk into a NumPy array (BGR order), and demonstrates the format-conversion, resize, and save round-trip.

import cv2

img = cv2.imread("cat.jpg")              # load -> BGR uint8 array
gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)   # drop color -> single channel
small = cv2.resize(gray, (128, 128))       # force a fixed size
cv2.imwrite("cat_small_gray.png", small)  # save back to disk
# cv2.imshow("preview", img)          # opens a native window (scripts only)
interpretation

imread returns None (not an error) if the path is wrong — a check you'll rely on constantly in File 3 for detecting corrupted files.

when NOT to use cv2.imshow

It requires a GUI backend and doesn't work in Jupyter notebooks or headless servers — use Matplotlib's imshow instead in those environments (next section).

The scikit-image equivalents, for comparison:

from skimage import io, color, transform

img = io.imread("cat.jpg")                       # RGB order, not BGR
gray = color.rgb2gray(img)                     # returns float64, 0.0-1.0
small = transform.resize(gray, (128, 128))
⚠ common mistake

scikit-image's rgb2gray returns floats in 0.0–1.0, while OpenCV's cvtColor returns uint8 in 0–255. Comparing or combining outputs from the two libraries without checking dtype and range first produces images that look "washed out" or all-black for no obvious reason.

07 Visualization

Matplotlib is the workhorse for actually looking at images and arrays inside notebooks and scripts.

what it does

Displays a color image and a grayscale image side by side, correctly.

import matplotlib.pyplot as plt

fig, axes = plt.subplots(1, 2, figsize=(8, 4))

axes[0].imshow(rgb_image)
axes[0].set_title("Color")
axes[0].axis("off")

axes[1].imshow(gray_image, cmap="gray")
axes[1].set_title("Grayscale")
axes[1].axis("off")

plt.tight_layout()
plt.show()
common mistake

Forgetting cmap="gray" on a 2D array. Matplotlib defaults to a yellow-purple "viridis" colormap for single-channel data — the image isn't corrupted, it's just being colorized by default.

08 First mini project

A small, real "dataset" — five classic sample images bundled with scikit-image, deliberately mixed in shape and color mode, just like a messy real dataset would be.

what it does

Loads all five images, prints their shape/dtype/min/max/mean, and separates the color ones from the grayscale ones.

from skimage import data

images = {
    "astronaut": data.astronaut(),
    "chelsea":   data.chelsea(),
    "coffee":    data.coffee(),
    "camera":    data.camera(),
    "coins":     data.coins(),
}

for name, img in images.items():
    kind = "RGB" if img.ndim == 3 else "grayscale"
    print(f"{name:10s} shape={str(img.shape):15s} dtype={img.dtype} kind={kind} mean={img.mean():.1f}")
expected output
astronaut  shape=(512, 512, 3)   dtype=uint8 kind=RGB       mean=114.6
chelsea    shape=(300, 451, 3)   dtype=uint8 kind=RGB       mean=115.3
coffee     shape=(400, 600, 3)   dtype=uint8 kind=RGB       mean=98.6
camera     shape=(512, 512)      dtype=uint8 kind=grayscale mean=129.1
coins      shape=(303, 384)      dtype=uint8 kind=grayscale mean=96.9
interpretation

Even five "clean" sample images already differ in resolution, aspect ratio, and color mode. A real dataset pulled from the internet will vary far more — this is exactly what Section 2 (dataset-level EDA, File 2) exists to catch systematically.
